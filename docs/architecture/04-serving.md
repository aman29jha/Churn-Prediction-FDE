# Serving — Real-Time API + Operational/Analytical Split

![Serving architecture](diagrams/04-serving.svg)

## Current implementation status (read this before the design below)

The DynamoDB fast path described below is now real: `src/service/app.py`'s
`/score/{customer_id}` reads live, per-request, from the `customer_scores`
DynamoDB table (`src/service/dynamodb_client.py`). Every `gold_transform`
run writes each customer's current feature vector + `churn_probability` +
segment there (`scripts/spark_job_entrypoint.py --dynamodb-table`), so a
score reflects the latest Gold run immediately — no pod restart needed,
closing the gap this section used to describe.

One piece of the original target design is still not built: true
on-the-fly cold-start compute (deriving RFM features from raw Silver
events for a customer with no Gold row at all, e.g. one added between Gold
runs). What exists instead is a two-tier lookup — DynamoDB first, falling
back to the static JSON snapshot (`models/customer_scores.json`, synced
from S3 at pod startup) only if DynamoDB has no row either. A `customer_id`
missing from *both* still returns a `404`, not a computed score. Stated
honestly as the one remaining gap, not glossed over.

## Two stores, two purposes

A standard, deliberate pattern rather than one store trying to do both jobs:

- **Athena / Iceberg Gold tables** — the **analytical** layer. Ad-hoc marketing queries ("give me everyone in the Hibernating segment"), dashboards, the reviewer console's aggregate views. Query latency of 1-2+ seconds is fine here.
- **DynamoDB `customer_scores`** (keyed by `customer_id`, written by the Gold Spark job after each run) — the **operational** layer. Fast, O(1) point lookups for the real-time API. Querying Athena per API request would be far too slow for live scoring.

## `/score/{customer_id}`

1. Request hits the ingress (TLS termination) -> auth middleware -> rate limiter -> FastAPI.
2. **Fast path** (real, deployed): look up the latest precomputed score in DynamoDB — written by the last `gold_transform` run, which now scores customers using a rolling `as_of=now()` (`--live-scoring`, see [01-data-platform.md](01-data-platform.md)) rather than a fixed historical cutoff, so this genuinely reflects current data.
3. **Cold-start fallback** (DynamoDB has no row — e.g. before Gold has ever run): the static JSON snapshot synced from S3 at pod startup. Still a gap: true on-the-fly compute from raw Silver events for a customer in neither store isn't built — see "Current implementation status" above.
4. Response includes the probability, the RFM segment, and (for the console) a SHAP-based explanation — see [../modeling.md](../modeling.md).

## Auth, rate limiting, tracing

- **Auth**: bearer token validated at the API layer (`require_auth`, `src/service/app.py`); the live simulator's token lives in a Kubernetes Secret, injected as an env var — this is our service-to-service auth story. Uniqueness of an individual event is a separate concern from request auth — see [02-simulator.md](02-simulator.md) for how `event_id` is defined and what that does and doesn't protect against.
- **Rate limiting**: a sliding-window limiter (per-client-IP timestamp deque, `_check_rate_limit`) in front of every route, protecting against a runaway simulator misconfiguration or an abusive caller. Applied uniformly across routes and per-pod (in-memory) — not yet tuned per-endpoint or shared across replicas, both reasonable follow-ups if this scaled beyond one `api-service` pod.
- **Tracing**: not yet built. AWS X-Ray end-to-end (ingress -> API -> DynamoDB/S3 -> response) was in the original design as a real per-hop latency breakdown, but only the aggregate API p99 latency metric exists today — an honest gap, not a silent one. See [05-observability.md](05-observability.md).

## Ingress

ALB or nginx ingress (Terraform-managed), fronting both the scoring/ingest API and the Streamlit reviewer console (separate route, separate auth — see [06-reviewer-console.md](06-reviewer-console.md)) — this is the concrete answer to the assignment's "how does this integrate with the platform's existing ingress/gateway stack" requirement.

## Future extension: bulk file-based ingestion via pre-signed S3 URLs

`/events/ingest` today only accepts one shape of client: a caller that already holds a bearer token and can make a synchronous HTTP POST with a JSON batch (see [02-simulator.md](02-simulator.md) for the batch shape). A real integration partner often instead wants to drop a bulk export file — thousands of events at once, generated by their own batch job — without wiring up per-event API calls. Design for that, not yet built:

- **Auth still happens first, against our service** — a new authenticated endpoint (same `require_auth` bearer-token check as today), e.g. `POST /ingest/upload-url`, that a client calls to request a place to drop a file.
- **We hand back a short-lived, scoped S3 pre-signed PUT URL** (`boto3` `generate_presigned_url`, a few minutes TTL, a `Content-Length` ceiling) targeting a key under our own `bronze/` prefix — e.g. `bronze/uploads/<client_id>/<uuid>.json`. The client uploads directly to S3; our service is out of the data path entirely after minting the URL.
- **Deliberately our bucket, not theirs.** The alternative — ingesting from a *customer-owned* S3 bucket via cross-account IAM role assumption — was considered and rejected for now: it needs per-customer trust-policy setup and a materially larger security surface (cross-account access), for a capability the pre-signed-URL approach already delivers with far less new infrastructure.
- **No new orchestration needed.** A file landing under `bronze/` via a pre-signed PUT triggers the exact same S3 Event -> SNS -> SQS -> Lambda -> `medallion_pipeline_dag` chain that already exists (see [03-orchestration.md](03-orchestration.md)) — the trigger chain doesn't know or care whether the object arrived via `/events/ingest`'s direct write or a pre-signed upload.
- **The real design gap this introduces**: today, nothing malformed ever reaches Bronze, because Pydantic (`RawEvent`/`IngestBatch`, `src/service/schemas.py`) validates every event *before* anything is written. A pre-signed upload bypasses that entirely — the file lands in Bronze unvalidated. `silver_transform`'s existing quarantine-by-`event_type` logic (`dropDuplicates` + filter against `KNOWN_EVENT_TYPES`) becomes the actual validation gate for this path instead of a synchronous `422` response, which is a meaningfully different failure mode (a bad file gets silently quarantined downstream, not rejected at upload time) and would need its own visibility — e.g. a quarantine-count metric per source file.
